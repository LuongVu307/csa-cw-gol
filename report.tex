\section{Parallel Implementation}

\subsection{Functionality and Correctness}

Our primary parallel implementation uses map-reduce to evolve a two-dimensional
board whose cells are represented by bytes: 255 for alive and 0 for dead.
Each cell's next state depends on its eight neighbours. Both dimensions wrap
around, producing a toroidal board. The board dimensions, number of turns,
and requested worker count are supplied through \texttt{gol.Params}.

The implementation reports initial live cells and subsequent cell changes
through an event channel, allowing SDL to display progress. It also supports
PGM snapshots, pause/resume (\texttt{p}), saving (\texttt{s}), and quitting
with output (\texttt{q}). A two-second ticker requests an alive-cell count;
the simulation loop handles this request between turns, so reporting can be
delayed by a long turn or blocked event delivery. Normal completion outputs
the final board and waits for I/O completion before emitting
\texttt{ImageOutputComplete} and the \texttt{Quitting} state. The final
simulation-result event itself is emitted before image writing.

\subsection{Concurrency and Synchronisation}

\paragraph{Distributor architecture.}
The distributor loads the board through PGM I/O and emits initial live-cell
events for SDL. A \texttt{completeTurn} callback separates calculation from
common controls and output. The outer loop forwards keyboard commands through
unbuffered channels; a simulation goroutine started with \texttt{wg.Go(loopFn)}
owns board updates and handles commands between generations
(Figure~\ref{fig:parallel-flow}). The outer loop never modifies the board.

Worker results and controls use channels, while workers share board-row
references. The I/O link represents command, data and acknowledgement channels;
a helper goroutine (not shown) waits for worker completion.

\paragraph{Map-reduce~architecture.}
\texttt{startWorkersMapReduce} partitions the board into horizontal strips,
distributing remainder rows and including read-only halo rows with toroidal
wrap-around. Starting-row offsets map results to global coordinates. Each
turn launches workers with \texttt{wg.Go(...)}; execution depends on available
CPUs and \texttt{GOMAXPROCS}. Workers build local change lists and send
coordinates through the shared buffered \texttt{cellFlippedChan}. The
one-worker path calculates directly in the simulation goroutine.

The simulation goroutine collects coordinates while workers run, preventing
a full channel from blocking worker completion. A helper waits for all workers,
signals completion and closes the channel; the collector then drains it.
Receiving coordinates may overlap with worker reads; applying flips
must wait until every worker has finished and every result has been collected.
Earlier updates could mix generations during neighbour counting and produce
scheduling-dependent results. The simulation goroutine applies the flips and
reuses the coordinate buffer for \texttt{CellFlipped} events, avoiding a full-board
comparison. It then advances the turn count and emits \texttt{TurnComplete}.
Collection, updates and event delivery remain serial; worker goroutines and
local change lists are created each turn.

\paragraph{Controls and periodic reporting.}
A \texttt{select} handles ready commands and ticker events; otherwise its
\texttt{default} branch calculates a turn unless paused. Commands run between
turns, so snapshots and counts describe complete generations. Pause leaves
save, quit and reporting available, but the default branch keeps polling and
can consume CPU. The two-second ticker requests alive counts rather than
pacing calculation; long turns or blocked event delivery delay responses.

\paragraph{Output and termination.}
Saving waits for I/O acknowledgement before emitting
\texttt{ImageOutputComplete}. At natural completion, the simulation signals
\texttt{doneSig} and returns; the outer loop joins it and writes final output.
On quit, the simulation writes output itself and \texttt{quitFlag} prevents
repetition. The distributor's wait group joins the simulation before closing
the event channel; a separate wait group tracks calculation workers.
\texttt{FinalTurnComplete} precedes image writing, while
\texttt{ImageOutputComplete} and \texttt{Quitting} follow I/O acknowledgement.

\subsection{Memory Strategies}

All three strategies use the same Game of Life rules and common distributor
control logic. They differ in how workers represent and combine next-state
results. This allows the evaluation to compare allocation, synchronisation,
and event-generation costs under a common workload.

\end{table*}

\paragraph{Memory ownership and safe updates.}
Heap workers read the source board and write newly allocated, private strips;
receiving all strips completes the generation before the coordinator replaces
the board. Double-buffer workers read only the source and write disjoint strips
of the destination, so their writes do not overlap.
The coordinator waits for every completion signal before comparing or
swapping the boards. Otherwise, a late worker could still be writing a board
that has become the next generation's input. Map-reduce workers only read the
board; the simulation goroutine alone applies the collected flips after their
completion. In all three strategies, save and quit stream the board between
turns and wait for I/O completion before simulation continues, preventing a
snapshot from being changed while it is being written.

Heap allocation is expected to incur repeated board-result allocation,
whereas double buffer avoids that allocation but still compares every
cell to generate events. Map-reduce also examines every cell, even when
few cells change; however, its result collection and update work depend on
the number of changes. Dense changes may make coordinate storage and
per-coordinate channel operations expensive. These are design expectations;
the evaluation must establish their effect on measured runtime and memory
use.

\section{Parallel Evaluation}

\subsection{Experimental Methodology}

We investigated how memory strategy, worker count and board size affect
runtime and allocation. Each of the three local distributors was tested
with 1, 2, 4, 8, 12 and 16 workers on the supplied $128\times128$ and
$512\times512$ images - 36 configurations in total. Comparisons between
strategies keep image and worker count fixed; scaling comparisons vary workers
within the same strategy and image. The images contain different
patterns, so comparisons between sizes also reflect differences in activity.

Every benchmark operation restarted the original image and simulated
100 turns. Measurements used Go 1.25.0 on WSL2 with an Intel i7-10750H
(six cores, twelve logical CPUs), \texttt{GOMAXPROCS=12} and normal garbage
collection. Each configuration had five samples with a one-second benchmark
target per sample. We report median runtime, cumulative allocated bytes and
allocation count per operation. Range bars show observed minima and maxima,
not confidence intervals.

For strategy $s$, board size $b$ and worker count $n$, speedup is
\[
S_{s,b}(n)=\frac{T_{s,b}(1)}{T_{s,b}(n)},
\]
where $T_{s,b}(n)$ is the median runtime for a fresh 100-turn simulation.
Each strategy and size uses its own one-worker baseline, so speedup measures
scaling within that implementation. For example, double buffer on
$512\times512$ takes 1180.22\,ms with one worker and 306.95\,ms with twelve,
giving $3.84\times$ speedup. Ideal scaling gives $S(n)=n$; serial work,
coordination and hardware limits reduce this gain. We compare absolute runtime
alongside speedup because the strategies have different baseline costs.

The benchmark runs the actual local distributors with in-memory I/O and an
event consumer. Timing includes channel setup, board allocation, initial
pixel transfer, calculation and coordination, event handling, final alive-list
construction and final pixel transfer. Input-file reading, disk output, SDL
rendering and reference validation are excluded. The results therefore
measure the simulation with event handling; they do not isolate the
cell-update kernel. Allocation totals also include the harness.

Before timing, all 36 configurations matched an independent serial reference
for the final board and completed-turn counts. The $512\times512$ reference
also matched the supplied 100-turn fixture. A separate recorded race-detector
run passed at 1, 4 and 12 workers for both sizes and all strategies. This
provides evidence for the measured calculation paths, but does not verify
keyboard handling, SDL behaviour or every worker configuration under the
race detector.

\subsection{Performance and Scaling}

\paragraph{Increasing workers gives diminishing benefit.}
All three strategies become substantially faster as workers are added, but
improvement generally levels off around 8-12 workers
(Figure~\ref{fig:parallel-runtime}). On $128\times128$, the lowest full-run
median for each strategy occurred at 12 workers: 28.54\,ms for heap
allocation, 27.45\,ms for double buffer and 27.79\,ms for map-reduce.
None improved at 16 workers. On $512\times512$, heap allocation and
map-reduce still improved slightly from 12 to 16 workers (309.06 to
302.70\,ms and 342.00 to 333.71\,ms), whereas double buffer rises
from 306.95 to 320.10\,ms. Thus 8-12 workers marks worse returns,
rather than always improving. Double buffer and map-reduce have close
medians and overlapping sample ranges, so these measurements do not
conclude which is the better method.

Adding workers divides the cell calculations into smaller pieces, but other
work still takes time. The coordinator collects results and sends events
sequentially. Each turn also requires creating workers and waiting for all
of them to finish. As workers receive less calculation, these remaining
costs can limit further improvement. With \texttt{GOMAXPROCS=12}, at most
twelve goroutines can execute Go code at once, so sixteen workers must
share the available execution slots. These factors could explain why
adding workers eventually gives little benefit, but we would need profiling
to determine which factor has the greatest effect.

\paragraph{The larger input benefits more from parallel calculation.}
At 12 workers, heap allocation's speedup rises from $1.83\times$ on
$128\times128$ to $2.56\times$ on $512\times512$; map-reduce's rises from
$2.56\times$ to $3.29\times$, and double buffer's from $2.71\times$
to $3.84\times$. More calculation per turn can spread coordination costs
over more work. However, the larger input also contains a different pattern,
so this comparison cannot isolate the effect of board size. Its 16-fold
increase in cell count produces runtime increases of approximately
$10.8\times$, $11.2\times$ and $12.3\times$ for heap allocation, double
buffering and map-reduce respectively at 12 workers. These workload
comparisons do not establish sublinear complexity in cell count.

\paragraph{Greater speedup does not necessarily mean lower runtime.}
On $512\times512$ at 12 workers, map-reduce achieves $3.29\times$ speedup
and heap allocation $2.56\times$, yet heap allocation is faster in absolute
terms: 309.06\,ms compared with 342.00\,ms. Heap allocation starts from a
faster one-worker baseline. Double buffer achieves $3.84\times$ speedup
and a 306.95\,ms median, close to heap allocation, although its sample
range is wider (304.55--409.39\,ms versus 301.62--313.37\,ms).
The baselines also use different paths: heap allocation launches a strip
worker, whereas double buffer and map-reduce calculate directly on the
full board. Their transition from one to two workers therefore changes
both worker count and execution path. Speedup describes scaling relative
to these baselines; absolute runtime is needed to compare strategies.

\subsection{Allocation and Memory Behaviour}

\paragraph{Double buffer consistently allocates fewer bytes.}
At matched size and worker count, double buffer has the lowest cumulative
allocation throughout the measured configurations
(Figure~\ref{fig:parallel-allocation}). At 12 workers on $512\times512$,
it allocates 9.90\,MiB per 100-turn simulation, compared with 38.42\,MiB
for heap allocation and 25.92\,MiB for map-reduce. The corresponding
$128\times128$ totals are 0.73, 3.31 and 1.92\,MiB. Reusing the two
boards avoids the repeated output-strip allocation of the heap strategy.
Map-reduce avoids replacement boards, but its workers still allocate local
coordinate lists. These totals measure cumulative allocation, not peak RAM.

\paragraph{More workers increase allocation counts without a matching rise in bytes.}
On $512\times512$, increasing workers from 1 to 16 raises allocation counts
from approximately 432,000 to 440,000 for heap allocation, 381,000 to 383,000
for double buffer, and 382,000 to 399,000 for map-reduce. The smaller
input shows the same upward trend. Extra worker coordination and result
objects each turn are consistent with this increase. Yet allocated bytes
remain near 38--39\,MiB for heap allocation and roughly 10--11\,MiB for
double buffer. Map-reduce's bytes fall from 33.05\,MiB at one worker
to a minimum of 25.65\,MiB at eight, then rise to 26.34\,MiB at sixteen.
Partitioning changes the local lists and their capacities, which could
contribute to this behaviour; the measurements do not isolate the cause.
The two graphs consequently distinguish the number of allocations from
their combined size: more allocations can coexist with fewer total bytes.

\paragraph{Larger inputs increase allocation, but allocation alone does not predict speed.}
At 12 workers, moving to the larger input increases allocated bytes by
roughly 12--14 times across the strategies. Allocation counts rise by about
11 times for heap allocation and 16 times for the other two. Board storage,
row objects, events and change lists contribute differently, so these
outcomes need not scale identically with cell count. The different patterns
also affect event and coordinate-list workloads. Although double buffer
allocates substantially fewer bytes, it is not consistently fastest in the
full-run timings. Without garbage-collector traces or profiles, we cannot
attribute runtime differences to garbage collection or estimate how much
time it consumes.

\subsection{Findings and Limitations}

Adding workers reduces runtime before gains level off; double buffer
consistently reduces cumulative allocated bytes. Runtime rankings change in
the confirmation run, so no strategy is consistently fastest.

Results cover two supplied patterns over 100 turns. Density and event costs
were not isolated, and fixed execution order and WSL host conditions may bias
comparisons. Different single-worker paths and strip construction also mean
that the comparison varies more than memory policy alone. Profiling and
controlled pattern experiments would help explain the observed costs.

\section{Distributed Implementation}

\subsection{Functionality and System Design}

Our distributed implementation separates the local controller, broker and
worker services. The controller reads the input image, writes PGM output,
handles keyboard input and passes events to SDL. The broker owns the current
board and coordinates its evolution. Workers calculate changes for assigned
strips and return their results to the broker. Communication uses Go's
\texttt{net/rpc} over TCP. The controller obtains the broker address from
\texttt{brokerURL.txt}; the broker reads worker addresses from
\texttt{workerURLs.txt}.

The broker keeps control and board ownership in one place so workers can
focus on cell calculation. For multiple workers, each turn is divided into
horizontal strips with neighbouring halo rows. Workers return coordinates
of cells that need to change, rather than replacement boards. The broker
collects all results before applying the flips, so every worker calculates
from the same generation. This extends the local map-reduce design across
processes, although transmitting coordinates can be expensive when many
cells change.

\subsection{Communication and Control}

\paragraph{Starting and calculating turns.}
The controller starts a run by sending the parameters and initial board
through the \texttt{ProcessStart} RPC. The broker connects to the configured worker
addresses and reuses those connections during the simulation. At each turn,
it sends each worker its strip, two halo rows and a starting-row offset.
The halo rows supply neighbours across strip boundaries, including vertical
wrap-around; the offset converts local coordinates to global board positions.
Workers return lists of changed cells. They do not exchange messages directly
with one another or retain their own evolving board between requests.
Consequently, the broker sends strip pixels again each turn.

The configured address count determines the number of strips; the
controller's requested \texttt{Threads} value does not select the number of
remote workers. There is also a special case: with one address, the shared
map-reduce helper calculates the board locally in the broker. A connected
worker is therefore not necessarily doing calculation. This case must be
changed before using one remote worker as a distributed benchmark baseline.

\paragraph{Displaying progress and returning output.}
The controller repeatedly calls \texttt{Broker.ProcessNextTurn} to receive
ordered batches of changed coordinates, producing \texttt{CellsFlipped}
and \texttt{TurnComplete} events for SDL. Initial live cells are sent before
the first \texttt{Executing} state. The broker copies each turn's coordinate
list because its reducer reuses its buffer. A bounded channel limits queued
batches, but also means a slow controller can hold up the simulation.
Normal completion returns the final board and completed-turn count for
local PGM output. Every two seconds the controller also requests an alive-cell
count; this uses a copy of a board protected against concurrent updates.

\paragraph{Keyboard controls.}
Save (\texttt{s}), pause/resume (\texttt{p}) and quit (\texttt{q}) use separate
RPC methods. Save returns a board copy and its turn number for local output.
The engine handles these controls between turns, so snapshots describe
complete generations and commands cannot interrupt an ongoing calculation.
Quit returns a snapshot while leaving the servers available for another run.
Kill (\texttt{k}) first stops the simulation and returns its snapshot; the
controller waits for image output to finish before requesting worker and
broker shutdown. This ordering lets the controller save the board before
the services exit.

\subsection{Extensions}

\paragraph{Halo Exchange and Broker-Worker Synchronisation Methods}
In the standard approach (explained previously), there is an
expensive synchronisation operation required between the broker and the workers,
in which the broker has to collect all of the results from the workers, put them together,
and then send out the resulting slices, all to be repeated for every single turn.

The halo exchange technique helps to reduce dependencies between the broker and the workers by
allowing the workers to directly communicate with one another without the broker needing
to collect all the workers' results. Then, once the workers have completed the required iterations,
they can return the final result to the broker, which can then return the result to the
local controller.

However, certain complications can occur when managing \texttt{quit},
\texttt{save}, \texttt{pause/unpause} and \texttt{cell count} events.
This is because there are limited guarantees on the arrival order and arrival time of
these events to the different workers. For example, say we have 2 workers, $W_{1}$
and $W_{2}$. Say that the broker recieves a \texttt{save} event, and then forwards
this to $W_{1}$ and $W_{2}$. It is completely possible for the \texttt{save}
event to arrive to $W_{1}$ on, say turn \texttt{42}, but to arrive to $W_{2}$
on turn \texttt{43}, or event \texttt{44}, and so on. This can be due to varying network
latencies between $W_{1}$ and the broker, and $W_{2}$ and the broker.

For simplicity, our solution uses a technique which involves sending multiple "synchronisation"
messages, which can be used to implement a "global" total ordering $R(s_{1}, E, s_{2})$, such
that $s_{1}, s_{2}$ are tuples of synchronisation messages that have been both sent (to all workers) and had an "acknowledgment"
message recieved (from all workers) completely before and after \texttt{E} respectively, and \texttt{E}
is a list of events to be processed by the workers. Using this ordering, we can use each synchronisation
message like a barrier after a set number of turns, at which each worker can respond to the message, then
process and respond to all events before being triggered by another synchronisation message to continue running
the GOL simulation.

Getting to some implementation details, sending synchronisation messages every turn (for example)
can sacrifice a lot of turns per second,
so it would be preferable to send synchronisation messages every couple of turns, with the target
begin to maintain a particular number of sync messages per second. The exact number for this must be
well chosen to find an appropriate balance between responsiveness to events and turns per second.

\section{Distributed Evaluation}

\subsection{Methodology and Scaling}

This benchmark asks whether four Go worker services complete the same
simulation faster than two. Each sample measures the elapsed time for an
entire 100-turn run, rather than the time for a single turn. It evaluates
process scaling over localhost TCP; the C++ halo-exchange extension is not
measured here.

We measured the Go distributed implementation on using
TCP connections between separate controller, broker and worker processes
on one WSL2 host. The machine used an Intel i7-10750H with twelve logical
CPUs and Go 1.25.0. Each process used \texttt{GOMAXPROCS=1}; this allows
separate workers to execute concurrently without giving each process
multiple Go execution slots. These are localhost measurements, not AWS
or multi-machine results.

The standalone harness (\texttt{benchmarks/distributed}) restarted the same
supplied $512\times512$ image for 100 turns, collecting three samples with
two workers followed by three with four. Fresh server processes were started
for each configuration, outside timing. Each sample established new controller
and worker connections. The broker's address list determined the actual
worker count; changing the controller's thread parameter alone would not.
The one-worker case was excluded because it calculates locally in the broker.

Timing included connection establishment, initial board transfer, worker
connections, generation calculation and reduction, streamed turn replies and
final-board transfer, including decoding and retaining change batches.
Process startup, fixture reading, reference validation, SDL and PGM writing
were excluded. All six samples returned the expected final board and exactly
100 ordered turn batches; replaying their changes also matched the supplied
100-turn fixture. These checks validate the measured paths, but do not replace
the keyboard and SDL tests. The raw CSV files, source hashes and environment
record are retained in
\nolinkurl{benchmarks/distributed/runs/20261119-083227}.

\paragraph{Measured scaling.}
Two workers took a median 486.70\,ms (range 446.42--555.59\,ms).
Four workers took 311.67\,ms (293.19--406.27\,ms),
a 36.0\% reduction (Figure~\ref{fig:distributed-runtime}). Relative speedup
was $T(2)/T(4)=486.70/311.67\approx1.56\times$, compared with
$2\times$ for ideal scaling when doubling workers. This is a two-worker
baseline, not speedup relative to serial execution. Four workers were faster
in these samples, but three repeats and two worker counts do not establish
an optimal configuration or a general scaling curve.

\paragraph{Expected scaling and communication costs.}
For width $W$, height $H$ and $n$ workers, each worker calculates approximately
$WH/n$ cells. Total worker requests carry $WH+2nW$ pixel bytes per generation
before encoding: the board partitions plus two halo rows per worker.
More workers reduce individual calculation but retain full-board transfer
and increase halo traffic and request count. Changed coordinates return to
the broker and are forwarded to the controller; their volume depends on
pattern activity.

The broker waits for the slowest worker, then performs central reduction
and stream copying. A slow controller can also block the bounded turn stream.
These costs are possible explanations for the observed sublinear improvement;
no profiling was performed to isolate their contributions. Localhost processes
share CPU and memory bandwidth. Fixed order, three repeats and uncontrolled
host load limit generalisation; more configurations, repeated or randomised
ordering and measurements on separate machines would be needed to establish
multi-node scaling. Timing boundaries also differ from the local parallel
benchmark, so subtracting those runtimes would not isolate network overhead.

\subsection{Failure Behaviour and Limitations}

The following assessment comes from code inspection, rather than injected
network-failure experiments. Failure to connect to the broker or a configured
worker causes a panic. More seriously, the worker calculation RPC discards
its returned error: a failed request can contribute no flips while the broker
continues with the other results, potentially producing an incorrect board.
A missing result is therefore not reliably distinguished from a strip with
no changes. There are no retries, worker replacement or application-level
RPC deadlines; an unresponsive service can hold up a generation.

The broker owns the only evolving board, so its failure loses the active
simulation. Workers are stateless between requests and cannot recover it.
If the controller disconnects, the broker's bounded stream can fill and
block progress; there is no cancellation or session-recovery mechanism.
Save and quit provide snapshots during normal operation, but do not provide
automatic checkpoint recovery after failure. The local functional checks do
not establish fault tolerance. Explicit error propagation, deadlines,
controller-disconnection handling and recoverable checkpoints would be the
next reliability improvements.

\section{Overall Findings}

Double buffering reduces allocation, while parallel runtime rankings depend
on the workload and run. The Go distributed baseline achieves $1.56\times$
localhost speedup from two to four workers; central reduction and repeated
board transfers remain scaling costs.
